# 联网策略：云是增强，不是依赖

> 结论先说：**联网躲不掉，但"必须联网才能用"躲得掉。**
> 这个产品的底线是——**断网之后，习惯和语音仍然完整可用。**

---

## 一、现状：纯局域网，没有云

```
手机 ──┐
       ├── 同一个 Wi-Fi ── server.py（电脑） ── 设备
       │                      SQLite 本地
       └── /album、家长页
```

- 设备**不直连公网**，只连局域网
- 所有数据在电脑上的 `coach.db`
- 唯一的外网依赖是 `ask_ai()`（问题罐的 AI 起草），而且**不配置也能用**（手动写答案）
- 没有账号、没有订阅、没有服务器运维成本

这套东西能一直跑，只要那台电脑在。

---

## 二、为什么你判断"联网无法避免"——四件会逼你联网的事

| 需求 | 现在怎么解决 | 联网后 | 逼你联网的程度 |
|---|---|---|---|
| **换语音包**（阶段升级） | 拔 SD 卡、拷文件、插回去 | 服务器下载 → 推给设备 | **必须**（否则每次升级都要拆机） |
| **问题罐 AI 起草** | 可选，调第三方 API | 已经是云依赖（可选） | 轻度 |
| **远程/多人**（出差时发认可、老人也能发） | 只能在同一 Wi-Fi | 云端中转 | 中度 |
| **备份**（电脑坏了怎么办） | 无 | 自动备份到对象存储 | 中度 |

第一条是**真痛点**：DFPlayer 只能读它自己 SD 卡里的文件，OTA 只能更新固件、写不了那张卡。
每换一次语音包，就要家长拆一次设备。

---

## 三、分层设计：四个等级，按需升级

### L0 · 纯离线（今天已经具备）
设备 NVS 缓存习惯表；断网时打卡进本地队列，联网后补传。
**断网可用性：100%（习惯 + 语音）**

### L1 · 局域网（当前）
手机与设备在同一个 Wi-Fi；数据在自家电脑。
**代价：0；隐私：最强**

### L2 · 单点云（建议的下一步）
只做三件事，其他一概不做：

1. **语音包分发**：服务器把 mp3 放进设备可读的位置（需要换硬件或用 SD 卡 Wi-Fi 模块）
2. **远程认可**：家长在外也能发一句（走云中转，设备仍只连局域网——由家里服务器代收）
3. **每日备份**：`coach.db` 加密增量备份到对象存储

**关键：设备依然不直连公网。** 一切出网走家里那台服务器。

### L3 · 全云（不推荐）
把逻辑搬到云端、设备当终端。
**后果**：订阅压力、服务终止风险、隐私风险——这正是 Skylight 被批评的地方（[$120 硬件 + $39/年](competitor-skylight-buddy.md)）。

## 四、四条不能破的红线

| # | 红线 | 理由 |
|---|---|---|
| 1 | **设备不直连公网** | 一个 5 岁半房间里的设备不该有公网出口；出网只走家里服务器 |
| 2 | **孩子的音频只到家里那台电脑** | 1.85 板载数字麦，默认关闭（`USE_MIC 0`）。开启后只做"按住说话"采集，音频**只传家里服务器**（局域网/回家同步），不进任何第三方云；7 天自动删、可一键清空。详见 [question-capture.md](question-capture.md) |
| 3 | **AI 不即兴生成给孩子听的内容** | 云可以帮大人写草稿，播给孩子之前必须过家长审核（现在的做法） |
| 4 | **数据以本地为主，云是副本** | 云挂了，本地还能跑；不能反过来 |

## 五、升级路径（不破坏现有架构）

```
今天：设备 ← LAN ← server.py ← SQLite（本地）
        │
L2：   设备 ← LAN ← server.py ← SQLite（本地，主）
                        │
                        ├─→ 对象存储（每日加密备份）
                        ├─→ 消息通道（远程认可中转）
                        └─→ 语音包分发（HTTP 下载，设备从服务器取）
```

改动集中在 `server.py`（加一个 `cloud.py` 适配层 + 一个开关），
设备端只在"取语音包"这一个点上需要改（而且那是换硬件时才做的事）。

---

## 六、语音包分发的三条路（按成本排）

| 方案 | 成本 | 是否需要换硬件 | 说明 |
|---|---|---|---|
| **A. SD 卡手动换** | 0 | 否 | 现状；每次阶段升级拆一次机 |
| **B. 换 I2S DAC + flash 存语音** | 中等 | **是** | 语音进 32MB flash，OTA 就能更新；顺带能播动态 TTS |
| **C. 云端 TTS 实时合成** | 低（代码） | 否 | 但破坏"AI 不即兴说话"和"爸妈的声音"两个原则，**不建议** |

**推荐顺序：A（现在）→ 换板时一并做 B。**

B 路线还有一个额外好处：语音不再受 DFPlayer 的 3000 条上限和"必须四位数字命名"的限制，
可以用"内容包"的方式管理（`voice/pack-L1/`、`voice/pack-L2/`）。

## 七、一张判断表：这个功能该不该联网

| 问 | 该联网 | 不该联网 |
|---|---|---|
| 断网时它还能不能用？ | 不能也行（增强） | **必须能用**（核心） |
| 数据出境吗？ | 只是副本 | 主数据 |
| 孩子会感知到延迟吗？ | 无所谓 | 会（打卡、语音必须 <1 秒） |
| 服务停止后呢？ | 退化但可用 | **产品死亡** |

**凡是"停服就死"的功能，一律不联网。**

---

## 八、一句话

> **联网是为了"让升级变容易"，不是为了"让产品变聪明"。**
>
> 云负责搬运（语音包、备份、远程的一句话），
> 本地负责陪伴（习惯、语音、卡片）。
> 这两件事一旦反过来，这个产品就变成了另一个 Skylight。
