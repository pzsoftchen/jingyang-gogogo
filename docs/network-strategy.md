# 联网策略：云是增强，不是依赖

> 结论先说：**联网躲不掉，但"必须联网才能用"躲得掉。**
> 这个产品的底线是——**断网之后，习惯和语音仍然完整可用。**

---

## 一、现状：纯局域网，没有云

```
手机 ──┐
       ├── 同一个 Wi-Fi ── server/server.py（电脑） ── 设备
       │                      SQLite 本地
       └── /album、家长页
```

- 设备**不直连公网**，只连局域网
- 所有数据在电脑上的 `coach.db`
- 唯一的外网依赖是 `ask_ai()`（问题罐的 AI 起草），而且**不配置也能用**（手动写答案）
- 没有账号、没有订阅、没有服务器运维成本

这套东西能一直跑，只要那台电脑在。

---

## 二、为什么你判断"联网无法避免"——四件会逼你联网的事

| 需求 | 现在怎么解决 | 联网后 | 逼你联网的程度 |
|---|---|---|---|
| **换语音包**（阶段升级） | 拔 SD 卡、拷文件、插回去 | 服务器下载 → 推给设备 | **必须**（否则每次升级都要拆机） |
| **问题罐 AI 起草** | 可选，调第三方 API | 已经是云依赖（可选） | 轻度 |
| **远程/多人**（出差时发认可、老人也能发） | 只能在同一 Wi-Fi | 云端中转 | 中度 |
| **备份**（电脑坏了怎么办） | 无 | 自动备份到对象存储 | 中度 |

第一条是**真痛点**：DFPlayer 只能读它自己 SD 卡里的文件，OTA 只能更新固件、写不了那张卡。
每换一次语音包，就要家长拆一次设备。

---

## 三、分层设计：四个等级，按需升级

### L0 · 纯离线（今天已经具备）
设备 NVS 缓存习惯表；断网时打卡进本地队列，联网后补传。
**断网可用性：100%（习惯 + 语音）**

### L1 · 局域网（当前）
手机与设备在同一个 Wi-Fi；数据在自家电脑。
**代价：0；隐私：最强**

### L2 · 单点云（建议的下一步）
只做三件事，其他一概不做：

1. **语音包分发**：服务器把 mp3 放进设备可读的位置（需要换硬件或用 SD 卡 Wi-Fi 模块）
2. **远程认可**：家长在外也能发一句（走云中转，设备仍只连局域网——由家里服务器代收）
3. **每日备份**：`coach.db` 加密增量备份到对象存储

**关键：设备依然不直连公网。** 一切出网走家里那台服务器。

### L3 · 全云（不推荐）
把逻辑搬到云端、设备当终端。
**后果**：订阅压力、服务终止风险、隐私风险——这正是 Skylight 被批评的地方（[$120 硬件 + $39/年](competitor-skylight-buddy.md)）。

## 四、四条不能破的红线

| # | 红线 | 理由 |
|---|---|---|
| 1 | **设备不直连公网** | 一个 5 岁半房间里的设备不该有公网出口；出网只走家里服务器 |
| 2 | **孩子的音频只到家里那台电脑** | 1.85 板载数字麦，默认关闭（`USE_MIC 0`）。开启后只做"按住说话"采集，音频**只传家里服务器**（局域网/回家同步），不进任何第三方云；7 天自动删、可一键清空。详见 [question-capture.md](question-capture.md) |
| 3 | **AI 不即兴生成给孩子听的内容** | 云可以帮大人写草稿，播给孩子之前必须过家长审核（现在的做法） |
| 4 | **数据以本地为主，云是副本** | 云挂了，本地还能跑；不能反过来 |

## 五、升级路径（不破坏现有架构）

```
今天：设备 ← LAN ← server/server.py ← SQLite（本地）
        │
L2：   设备 ← LAN ← server/server.py ← SQLite（本地，主）
                        │
                        ├─→ 对象存储（每日加密备份）
                        ├─→ 消息通道（远程认可中转）
                        └─→ 语音包分发（HTTP 下载，设备从服务器取）
```

改动集中在 `server/server.py`（加一个 `cloud.py` 适配层 + 一个开关），
设备端只在"取语音包"这一个点上需要改（而且那是换硬件时才做的事）。

---

## 六、语音包分发的三条路（按成本排）

| 方案 | 成本 | 是否需要换硬件 | 说明 |
|---|---|---|---|
| **A. SD 卡手动换** | 0 | 否 | 现状；每次阶段升级拆一次机 |
| **B. 换 I2S DAC + flash 存语音** | 中等 | **是** | 语音进 32MB flash，OTA 就能更新；顺带能播动态 TTS |
| **C. 云端 TTS 实时合成** | 低（代码） | 否 | 但破坏"AI 不即兴说话"和"爸妈的声音"两个原则，**不建议** |

**推荐顺序：A（现在）→ 换板时一并做 B。**

B 路线还有一个额外好处：语音不再受 DFPlayer 的 3000 条上限和"必须四位数字命名"的限制，
可以用"内容包"的方式管理（`voice/pack-L1/`、`voice/pack-L2/`）。

## 七、一张判断表：这个功能该不该联网

| 问 | 该联网 | 不该联网 |
|---|---|---|
| 断网时它还能不能用？ | 不能也行（增强） | **必须能用**（核心） |
| 数据出境吗？ | 只是副本 | 主数据 |
| 孩子会感知到延迟吗？ | 无所谓 | 会（打卡、语音必须 <1 秒） |
| 服务停止后呢？ | 退化但可用 | **产品死亡** |

**凡是"停服就死"的功能，一律不联网。**

---

## 八、一句话

> **联网是为了"让升级变容易"，不是为了"让产品变聪明"。**
>
> 云负责搬运（语音包、备份、远程的一句话），
> 本地负责陪伴（习惯、语音、卡片）。
> 这两件事一旦反过来，这个产品就变成了另一个 Skylight。

---

## 十、路线图：本地 POC → 云端（2026-11-02 决策）

> **决策**：POC 版本保持"家里服务器 + 局域网 + 离线队列"；
> **长期架构上云**，为的是**户外也能在线**（孩子在公园问"为什么树叶会变黄"时，当场就能被回应）。

### 三个阶段

| 阶段 | 联网形态 | 能力 | 代价 |
|---|---|---|---|
| **POC（现在）** | 家里 Wi-Fi | 在家全功能；出门靠 SD 缓存，回家同步 | 0 |
| **联机版** | 设备自己上网（4G/BLE 中继） | 户外即时响应 | 硬件 + 流量 + 云端运维 |
| **云端版** | 云端是主 | 多设备、远程、跨家庭 | 账号体系、合规、持续成本 |

### 户外联网的四种方案

| 方案 | 成本 | 功耗 | 复杂度 | 评价 |
|---|---|---|---|---|
| **家长手机开热点** | 0 | 设备低 | 每次手动开 | POC 之外最简单，但"每次都要开"注定用不久 |
| **BLE → 手机 App/小程序中继** | 0（硬件） | 低 | 要写手机端 | 手机在附近就行；但手机上得常驻一个 App |
| **4G Cat.1 模组**（Air780E 等） | ¥30–40 + 流量 1–2 元/月 | 峰值高（100–300mA） | 中 | **推荐**：真正独立联网，孩子问完几秒内就有回应 |
| eSIM / 内置模组 | 高 | 高 | 高 | 量产阶段再考虑 |

**推荐路径：BLE 中继先验证，4G Cat.1 再落地。**

理由：BLE 中继不用加硬件、不用交流量费，能先验证"户外即时响应"这件事孩子是否真的需要；
确认有价值后再上 4G——因为 4G 模组会显著改变电池策略（见下）。

### 4G 会带来的一个硬约束：功耗

Cat.1 模组峰值 100–300mA，比 Wi-Fi 还高。800mAh 电池 + 常态在线 ≈ 半天。

所以真正的设计是 **"离线优先 + 定时/事件唤醒"**：

```
平时：深度休眠（只留 RTC 闹钟）
有事：唤醒 → 联网 20 秒 → 传完立刻断网休眠
```

这恰好和"克制"的产品性格一致——**设备不该一直在线，它只在需要的时候醒一下。**

### 上云必然带来的 5 个改动

| # | 改动 | 影响 |
|---|---|---|
| 1 | **协议要版本化** | 现在是位置解析（`H=` 10 个字段），加字段就得全链路改。上云前后必须加 `V=2` 与"只追加不插入"的约定 |
| 2 | **设备身份与认证** | 现在服务器不认设备。上云要 `device_id` + token + HTTPS |
| 3 | **内容分层** | 固定语料（147 条 mp3）打包成**带版本的内容包**；动态答案走流式播放。两条路不能混 |
| 4 | **时钟一致性** | RTC / NTP / 服务器时间三者要对齐，否则"今天做了没"会算错 |
| 5 | **儿童数据合规** | 中国《儿童个人信息网络保护规定》要求监护人明示同意、最小必要、可撤回。上传孩子音频必须在家长页显式确认 |

### 现在就该做的 4 件"防返工"小事（约 60 行代码）

| # | 做什么 | 为什么现在做 |
|---|---|---|
| 1 | `state.txt` 加一行 `V=2`，并约定"新字段只追加在末尾" | 固件与服务器可以不同步升级，不用等齐 |
| 2 | 数据库加 `device_id` 列（现在恒为 `'poc'`） | 将来多设备不用改所有查询 |
| 3 | 语音内容包记录版本号（`content_pack` 表） | 将来 OTA 换语音包时能判断"设备上的是哪一版" |
| 4 | 设备凭证占位（`secrets.h` 加 `DEVICE_TOKEN`，服务器可校验可忽略） | 上云时不用改协议 |

### 隐私红线在云端版怎么改

POC 版的红线是"**音频只到家里那台电脑**"。
云端版必须改成可执行的承诺：

| 承诺 | 怎么做到 |
|---|---|
| 加密存储 | 音频静态加密，密钥不与数据同库 |
| 保留期 | 默认 7 天自动删，家长可改 |
| 可删可撤回 | 家长页一键删除该设备全部音频与衍生文本 |
| 不训练 | 写入服务条款；供应商侧关闭训练开关 |
| 最小必要 | 只上传"孩子说话那一段"，不含环境音（VAD 截断） |
| 监护人同意 | 首次开启采集时弹一次明确同意，可随时关闭 |

**注意**：这 6 条一旦上云就不是"设计选择"，而是**合规义务**。POC 阶段可以先不做，但数据结构要留出"这条音频属于哪台设备、哪次采集、何时到期"的字段。
